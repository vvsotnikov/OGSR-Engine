## What the activation experiment changes

`CALifeSimulatorBase::spawn_item` synchronously creates and registers a server object, creates supplies and invokes spawn callbacks before returning its pointer. Online switching occurs separately. Deferring that existing API would invalidate callers' immediate-use assumptions. The prototype therefore uses an explicit caller-owned queue in `SpawnQueue.lua`; it does not change the engine API or the campaign's spawn calls.

For the queued case, the driver processes requests in their original order until it reaches a 3 ms soft budget or eight creations in a frame. Each creation remains indivisible and may overrun the time budget. Results are stable server IDs; no raw server pointers are retained in the queue. Saving is allowed by this test only after all work finishes. This prototype is scoped to one loaded map and lacks production cancellation, save/resume, prioritization and cross-map lifecycle handling. Do not install it as a transparent replacement for synchronous spawning.

The driver separately records time inside creation, elapsed time to finish all requests, the online flag at each creation's return, and a once-per-second census of server retention, online flags and client objects. Consequently the reported first-all-online time is a sampled upper bound, not an exact activation latency. The creation/warmup peak covers both request processing and subsequent activation work.

All 400 synchronous creations returned with their online flag still false. All were first observed online 5.08–6.11 seconds after the batch completed. This separates the immediate server-creation cost from later activation. The existing level-registry iterator already has a time limit after its first update (`CSafeMapIterator::time_over`); no global online-switching policy was changed in this experiment.

Both budgeted runs reduced the worst frame by roughly 76% versus their corresponding synchronous compact runs. All 400 IDs remained retained, online and present on the client throughout measurement. The queue used at most five creations per step in these runs. Total creation work increased and completion was spread over about 1.4 seconds; it is not free work. First full online presence was observed about 6.08 seconds from creation start in both queued runs, overlapping the synchronous runs' roughly 5.35–6.37-second range. The one-second census and small sample prevent a strong claim about activation latency improvement.

The queued runs' largest frames occurred in stage 3, after all creation requests completed; neither peak had a creation batch in the preceding frame. The remaining 76–82 ms hitch is therefore not time spent executing one of the explicit creation batches. Activation, rendering, garbage collection and other engine work need a narrower trace before attributing it further. Steady-state mean frame times were 9.24 and 9.22 ms, with p99 18.86 and 18.02 ms. Different living populations/outcomes also limit direct comparison: these are not deterministic battles.

## Reproduction and manual build

```powershell
# After packaging the clean Release build as bin_regular:
./Prepare-RegularValidation.ps1  # requires a new destination directory
./Run-RegularValidation.ps1 -CompactQueue -SaveSnapshot
# Pass that session's appdata as SeedAppData and regular_validation as SaveName for cold reload.
./Run-RegularValidation.ps1 -Count 400
./Run-RegularValidation.ps1 -Count 400 -CompactQueue
./Run-RegularValidation.ps1 -Count 400 -CompactQueue -BudgetMs 3
python -B Summarize-Regular.py <session-directory>
python -B Test-Regular.py
```

`Start-RegularGame.ps1` and `D:/Games/OGSR-Baseline/Play-Regular-Whole-Map.cmd` launch the clean executable against the original installation, with private Bar saves, whole-map mode and scheduler compaction. They do not load the Lua driver, spawn test NPCs, collect frame CSVs or start Tracy. The regular build is available for the pending manual natural transition/task-hand-in test. Compaction remains opt-in; no existing launcher or gameplay binary was replaced.
