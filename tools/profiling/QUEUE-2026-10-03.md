# Scheduler queue compaction experiment

## Change and scope

`CSheduler::ProcessStep` previously erased each due item from the middle of a vector before invoking its callback. Every erase shifts the remaining items. The opt-in `-scheduler_compact` path instead clears that slot's object pointer, processes the remaining entries in the same order, and performs one stable removal of null slots before appending rescheduled items. It also removes tombstones left by unregistration. It does not sort the queue, change requested intervals, raise budgets, or skip NPC logic. The default path remains unchanged.

An unregister operation still scans the same vector and sees live entries, while self-unregistration uses the existing `m_current_step_obj` mechanism. Registrations remain deferred through the existing registration list. Retired item names may stay referenced until the end of the pass. Earlier cleanup of future-dated null entries has no callback; these are already unregistered objects. Wall-clock budget boundaries can change because less maintenance time is spent, so exact game outcomes need not be identical.

The per-frame stalker path was also inspected. Its inherited work includes movement/animation, network state, sound callbacks and sound-player dispatch; the stalker additionally updates physics, sight and weapon effects. These were left unchanged. Skipping them without finer attribution would risk behavior changes.

## Regression check

`scheduler-test` compiles the actual scheduler source and class definition against deterministic clocks and mock objects. Only includes and Windows SEH syntax are adapted. Across 200 scenarios and 20,000 scheduler steps, both implementations produced the same digest of callback order, callback time arguments, pending queue order/deadlines and scheduler budget evolution. Each executed 76,273 callbacks, 76,712 needed checks, 4,328 self-removals, 10,419 other-object removals and 1,799 callback registrations. Cases include not-yet-due items, expired/unused items, prefetch, budget exhaustion, re-registration and a non-mutating realtime callback. This is not a test of real Windows exception handling or all possible script reentrancy.

```powershell
cmake -S tools/profiling/scheduler-test -B <build-directory> -G "Visual Studio 17 2022" -A x64
cmake --build <build-directory> --config Release
ctest --test-dir <build-directory> -C Release --output-on-failure
```

CMake copies the scheduler at configuration time and tracks the original files as configuration dependencies. The fixture rejects diagnostic sources; restore gameplay sources first.

## In-game measurement method

Both paths use the same `bin_queue` executable, SHA-256 `DD01D602E0F5486B7EE4B02888AB6E72FC3A9DED37AB742E5A78753A570BFBE5`, based on `ac6bdee8e0d22cdd0cbfd848ccffdcb666ac65af` plus the optimization and archived diagnostics. Configuration is ReleaseTracyProfiler with no collector connected. Same Bar seed, hardware, settings, placement and 15/15/30-second readiness/warmup/measurement scheme as the earlier cadence sweep. Each run uses private appdata. No builds run during measured windows.

`QueueProbe.h` measures time around removal/tombstoning and final compaction/reinsertion, and the whole normal-priority scheduler step. These elapsed measurements include instrument overhead; they are not exclusive CPU time. Existing cadence probes remain enabled on both paths. Queue analysis uses the same roughly 29-second census-bounded interval as cadence; frame analysis covers the 30-second measurement stage. Maintenance per second is reported because a faster frame loop can perform more passes per second. The scenario remains stochastic and includes incidental combat; the +400 comparison uses legacy/compact/compact/legacy order to expose some run variation.

To rebuild the diagnostic package, apply `queue-diagnostic.patch` to clean gameplay sources containing the optimization; copy `CadenceStress.inl` to `ogsr_engine/xrGame/` and both `SchedulerProbe.h` and `QueueProbe.h` to `ogsr_engine/xr_3da/`. Build and package separately as `bin_queue`, retaining PDB, source patch, build log and manifest. Do not also apply the cadence patch: this patch already includes its hooks. The locally archived `bin_queue/source.patch` is the full diff against the recorded base commit.

```powershell
./Run-PopulationStress.ps1 -Counts 400 -QueueBenchmark
./Run-PopulationStress.ps1 -Counts 400 -QueueBenchmark -CompactQueue
./Run-PopulationStress.ps1 -Counts 20 -QueueBenchmark -CompactQueue -Combat
./Summarize-PopulationStress.ps1 -Session <session>
python -B Summarize-Queue.py <session>
```

Across the two +400 runs of each implementation, the mean of run-level mean frame times fell from 10.98 to 8.90 ms, about 19%. Mean measured queue-maintenance time per second fell by about 97%. The normal scheduler step averaged 2.89–2.99 ms/pass on legacy and 1.14–1.24 ms/pass on compact. No measured frame exceeded 33.33 ms. These are repeated short instrumented runs, not a confidence interval or a general FPS guarantee. The improvement was present in both orderings; simulation populations/outcomes were not identical.

All 436–439 stalkers observed alive throughout the +400 windows received updates, and all 400 spawned IDs remained online/retained throughout each measurement. The optimization reduced deadline lateness rather than achieving better frames by skipping scheduled thinking. The no-extra-NPC pair showed no meaningful frame improvement because the original absolute maintenance cost was small.

The bulk creation/activation spike remains: compact runs reached 282.59 and 285.50 ms during warmup. Queue compaction addresses ongoing scheduler overhead, not synchronous batch creation. Amortizing activation is a separate next investigation. Before enabling compaction by default, validate an ordinary non-diagnostic build and broaden lifecycle/campaign coverage.

The compact 20-fighter smoke test confirmed engagement with 66 shots from 19 fighters and 1,643 participant-enemy callbacks. Living fighters went from 20 to 16; their dispatch lateness was p99 6 ms, maximum 7 ms. No persistent-cohort NPC missed updates and no scheduler budget stop occurred. Mean frame time was 4.33 ms, p99 6.08 ms. First observed enemy selection still varied (median 934 ms, maximum 17.85 seconds), as in earlier unoptimized combat runs; this small stochastic encounter does not isolate perception/decision latency or prove identical combat outcomes.
